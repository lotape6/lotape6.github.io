    Dive 03.1The handle state machine

    A small part with a lot of states

    Client
    BMW Group, through Bertrandt Group (Seville)
    Period
    July 2022 – May 2024
    Target
    Neue Klasse cars with extendable door handles: BMW iX3 (2025), BMW i3 (2026)
    My part
    Software architecture and development of the extendable door-handle software
    Toolbox
    AUTOSAR C++, CAN / LIN / SOME/IP / DLT traces, GTest & GMock, Git, Scrum
    “Four Superbrains for the Neue Klasse” · BMW iX3 exterior · BMW USA
    1. S0 Retracted Flush. Low power; the handle controller waits for a wake-up from the vehicle access function.
    2. S1 Key detected The vehicle access function authenticates the digital key and asks the handle to extend. Vehicle-level signalling: CAN.
    3. S2 Extended · lit The actuator drives the handle out while its position sensor is monitored; the light strip comes on in darkness; the handle reports its state back. Local sensing and actuation in the door: LIN.
    4. S3 Grasped Capacitive sensing in the handle registers the grab and the handle raises an unlock request.
    5. S4 Unlocked · open The latch is released and the door reports ajar; the handle retracts once the door is closed and locked again.
    6. B1 Exit-warning hold If a road user is approaching, the exit warning holds the latch: the handle moves, the door doesn’t.
    7. B2 Mechanical redundancy With all electrics off, the handle can still be operated and a mechanical path to the latch opens the door.
    8. B3 Crash-safe state On a crash signal the function goes to its safe state: doors unlocked, handles reachable, and no automatic retraction until reset.

    Why a state machine. A handle that moves by itself has to be safe in every situation a car gets into: a dead battery, ice over the slot, a crash, a child pulling it while someone cycles past. The way to make that tractable is to name every state and every event explicitly, trace each transition back to a requirement, and test every transition in isolation with GTest and GMock before anything reaches a vehicle. That traceability, from requirement to state to test, was the backbone of my work.

    Where the buses come in. In general terms: vehicle-level decisions such as “the key is here, extend” travel over CAN from the access and body functions; sensing and actuation local to the door talk over LIN; richer service-based communication uses SOME/IP; and every component writes DLT logs. Most integration problems live between those layers, so most of my debugging was reading traces from all four side by side and finding the one message that arrived late, twice, or not at all. The X-ray view of the 3D door shows that layering physically: a controller, an actuator with its position sensor, a latch, and the harness between them.

    The three branches. The exit-warning hold, the mechanical redundancy and the crash-safe state are what make the part trustworthy. BMW reports that Euro NCAP confirmed the electrically operated handles kept working after all the crash tests and that a mechanical redundancy allows exit even if all electrical systems fail. The demo on this page shows the behaviour at the level BMW describes publicly; the real signal names, timings and thresholds are BMW’s and stay with them.

    Dive 04-AMakefiles → Bazel

    Why move a machine's software off Make

    A Makefile describes how to build: recipes, include paths, link lines. What it does not describe is what depends on what. Over years, a large C/C++ tree accumulates include paths that reach into other components, libraries that link because they always have, and two copies of the same symbol that only one linker order resolves. The build works, but nobody can prove why, and a full rebuild is the only safe one.

    Bazel inverts that. Every target declares its sources and its dependencies, and nothing else is visible to it. Hidden includes fail to compile. Circular dependencies fail to analyse. Duplicated symbols stop hiding behind link order. Once the graph is explicit it is also a DAG, so the build becomes incremental, cacheable and reproducible: the same inputs give the same outputs, on a laptop or a build farm.

    My part was the unglamorous half: assessing the debt first (cycles, duplicated symbols, declarations that disagreed with reality), then migrating large lithography-machine components target by target, and writing the automation and verification tooling that kept the migration honest. The toy below shows the shape of the change, not ASML's code.

    Switch

    Toolkit 02sessionizer · projects · flux-capacitor
    
    
    
      
    One keystroke between sessions
    
      
    
        
        
    
          
    
            
    Alt+q
    tmux-sessionizer: a tmux popup (87% wide, 73–80% tall depending on the window height) runs fzf over tmux list-sessions. Each row: name, window count, attached marker, age, current path.
    
            
    Preview
    right pane, 80% width: tmux capture-pane -p -e -J -S -, the full scrollback of the session's pane with colours, following the bottom. PgUp/PgDn scroll it, Home/End jump, ? and Alt+p toggle it, Alt+w cycles its position.
    
            
    Enter
    inside tmux: switch-client; outside: exec tmux attach-session. Outside tmux it is a zsh widget so fzf gets a TTY.
    
            
    Alt+w
    tmux-projects: fzf over tmuxinator YAMLs. Running projects show a live pane capture, the others their YAML through bat. Alt+o toggles preview mode, Alt+e edits the config and offers a restart.
    
          
    
        
    
      
    
      
    
        
    flux-capacitor came first: a Back-to-the-Future flavoured tmux session manager, inspired by sesh. flux connect <dir> warps into a session rooted at a directory and re-attaches if one exists; -p runs a command in every new pane, -P after the session ends, -e auto-loads an env file, -f forces a fresh session. flux launch builds a workspace from a .flux.yml. It has GitHub Actions integration tests (basic and daily).
    
        
    The sessionizer in the dotfiles is its successor: fewer features, one script, theme-aware symbols and colours, and the same promise that moving between projects costs one keystroke.

    The public pieces of a working harness
    
      
    
        
    A harness is everything around the model that makes its output predictable: what it reads first, what it may run, who checks its work, and which rules kick in automatically. These are the real files from three public repositories. The harnesses I run at work (hooks, evals, CI gates, per-directory rules, security reviewers) are company property and are only mirrored as structure in the explorer.
    
      
    
      
    
        
    
          
    1 · InstructionsAGENTS.md · opencode.json
    
          
    AGENTS.md describes stack, layout, commands and the hard rules (anti-ban, audit trail). opencode.json loads it plus TODOs.md into every session.
    
          
    "instructions": ["AGENTS.md", "TODOs.md"],
    
          
    - Never hard-delete jobs; tombstone via `is_active=False` + `job_events` entry.
- Anti-ban is a hard requirement: per-source rate limits, jitter, backoff on
  429/403, configurable cadence with enforced safe minimums. Do not bypass.
    
        
    
        
    
          
    2 · Permissionsopencode.json
    
          
    Bash is allowed, so the agent can run tests and commit, but destructive git and rm -rf ask first.
    
          
    "permission": {
  "bash": {
    "*": "allow",
    "git push*": "allow",
    "git commit*": "allow",
    "git reset*": "ask",
    "rm -rf*": "ask"
  }
}
    
        
    
        
    
          
    3 · Reviewer subagent.opencode/agents/reviewer.md
    
          
    Read-only (edit: deny). Checks anti-ban floors, the audit-trail rule, config safety, tests and docs. Verdict APPROVE / REQUEST CHANGES with file:line findings.
    
          
    mode: subagent
permission:
  edit: deny
  bash: allow
---
You are the code reviewer for alikindoi, a job-scraping tracker. You NEVER
modify files — you inspect and report.

1. **Anti-ban (hard requirement)** — reject any change that:
   - lowers a value in `HARD_MIN_INTERVALS` or bypasses `source_allowed()`
   - adds retries/loops against a job board (fail fast, skip, move on)
    
        
    
        
    
          
    4 · Commands.opencode/commands/test.md · ship.md
    
          
    /test runs pytest and the frontend build and fixes until green. /ship verifies, calls the reviewer, then commits and pushes.
    
          
    1. Run the verification suite: `backend/.venv/bin/pytest` and
   `npm run build` in `frontend/`. Stop and fix if not green.
2. Use the `reviewer` subagent (Task tool) to review `git diff HEAD` against
   the project rules. Address any REQUEST CHANGES findings first.
3. Inspect `git status` and `git log --oneline -5` for message style.
4. Stage only intended files (never `.env`, `data/`, or `node_modules/`),
    
        
    
        
    
          
    5 · Skills.opencode/skills/scraping-safety/SKILL.md
    
          
    Auto-triggers when adapters, runner, scheduler or rate limits are edited. Its rules override feature requests.
    
          
    description: Anti-ban and rate-limiting rules for alikindoi's scraping engine. Use when modifying adapters/, runner.py, scheduler.py, salary/description enrichment, config rate_limits, or adding a new job-board source.
---
This project's survival depends on NOT getting banned by job boards. When
touching scraping code, these rules override any feature request.
